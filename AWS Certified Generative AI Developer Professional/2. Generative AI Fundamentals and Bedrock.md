# Generative AI Fundamentals and Bedrock

Amazon Bedrock is a serverless API over many foundation models, so an application can swap models without rewriting against each vendor. This section is how you add your own data (fine-tuning or retrieval), control generation, and keep the result safe and cheap enough to run.

## Bedrock

A **foundation model** is a large pretrained transformer. Examples in Bedrock: Claude (strong at Q&A and multi-step workflows), Llama, Amazon Nova (including Nova Reel for video and Nova Canvas for images), Amazon Titan (mainly embeddings; also text), Stable Diffusion, and Cohere. Jurassic-2 is multilingual and shows up more on AI Practitioner than here. Models are added and removed constantly; learn capabilities, not a catalog screenshot.

Bedrock sits in front of those models with one API. Invoke chat, text, or image models, or your own fine-tuned model. It is serverless. SageMaker is the path when you need more control over deployment. Usage of a non-Amazon model is a Marketplace line on the same AWS bill, priced per model. Check [Bedrock pricing](https://aws.amazon.com/bedrock/pricing/) before you pick one. There is no free tier.

Two planes:

| Plane | What you call | Use |
|---|---|---|
| Bedrock | Manage, deploy, fine-tune | Control plane |
| Bedrock Runtime | `Converse`, `ConverseStream`, `InvokeModel`, `InvokeModelWithResponseStream` | Inference |
| Bedrock Agent | Manage agents and the knowledge bases they use as tools | Build agents |
| Bedrock Agent Runtime | `InvokeAgent`, `Retrieve`, `RetrieveAndGenerate` | Run an agent or query a knowledge base directly |

Use an IAM user, never the root account. `AmazonBedrockFullAccess` for building; read-only when the principal only calls the model. The region must support Bedrock.

**Model access** is supposed to be on by default, and billing starts when you invoke. Anthropic is the exception: the first time you select Claude you submit a use case (it approves immediately). Some accounts have on-demand token quota set to 0. `ThrottlingException` / "Too many tokens per day" means open a support case and raise the quota. Set a [[1. Introduction|billing alarm]] first.

## Inference settings

The playground is where these show up. Chat mode keeps prior turns in context. Single-prompt mode does not; not every model supports it (Haiku does not). Compare mode runs one prompt on two models, and each model has its own config, so match them or the comparison is meaningless.

- **System prompt**: instructions applied to the whole conversation
- **Reasoning**: extra chained steps for a hard request. Costs more tokens
- **Max output tokens**: cap length and spend
- **Stop sequences**: end generation on a custom marker, not only a newline
- **Temperature**: randomness of the next token. Lower is more deterministic. Default in the playground is often 1
- **Top-p**: probability mass of candidate tokens. **Top-k**: how many candidates to sample. Same creativity lever, different cut
- **Prompt caching**: reuse a repeated prefix (system prompt, standing instructions) at a lower token rate
- **Prompt router** (Nova or Anthropic): sends an easy prompt to a small model and a hard one to a large model. Saves money when the router is right; a hard prompt sent to Haiku comes back worse

Image models add a negative prompt, size, color palette, a conditioning image, prompt strength, and a seed. The same seed is how you get a repeatable image.

## Converse API

`POST /model/{modelId}/converse` is the stable message API, so you can change `modelId` without changing the call. The exam will not ask you to write it. Minimum is `modelId` plus `messages` (each message has a `role` and `content`). A stored Prompt Management prompt can stand in for the text.

Optional fields that map to the rest of this section: `system`, `inferenceConfig` (`maxTokens`, `stopSequences`, `temperature`, `topP`), `guardrailConfig` (`guardrailIdentifier`, `guardrailVersion`), `toolConfig` (`tools`, `toolChoice`), `outputConfig.textFormat` for a structured schema, `promptVariables`, `performanceConfig.latency`, `serviceTier`, and `additionalModelRequestFields` for model-specific knobs.

## Adding your own data

Fine-tuning bakes data into the model. RAG leaves the model alone and pastes retrieved text into the prompt. Pick from how often the data changes and what you will pay now versus on every call.

| | Fine-tuning (custom model) | Continued pre-training | RAG (knowledge base) |
|---|---|---|---|
| Data | Labeled prompt/completion pairs in S3. Images: prompt plus an S3 image | Unlabeled raw text | Documents queried at request time |
| Effect | New model id. Same API as the base model. Can fine-tune a fine-tune | Extra text is in the model, so prompts stay short | Prompt grows by the retrieved chunks |
| When | Stable style, voice, or a new task (classification). Data newer than the cutoff. Proprietary examples (past tickets, emails) | A corpus you want memorized, with no Q&A labels | Data that changes. "AI search." Avoid retraining |
| Cost | Expensive and slow up front. Cheaper later because prompts stay small | Same | Cheap to update. Token cost on every prompt. Vector storage is not cheap |
| Training? | Yes | Yes | No. The data is context, not weights |

Not every model can be fine-tuned. Read the model card. Titan, Cohere, and Meta are the examples that can. Sensitive training data goes through a VPC with PrivateLink.

RAG is an open-book exam: embed the question, fetch the nearest passages, append them to the prompt, then generate. The base model's own training still applies, so it can still hallucinate, and a bad chunk makes a bad answer. Quality hinges on chunking, how many neighbors you keep ($k$), and the wording of the prompt that wraps the hits. It is also non-deterministic, so it is awkward to test. A vector store is the usual database; a graph store (recommendations, a knowledge graph) or classic TF-IDF can be the retriever, including a hybrid of both.

## LoRA

**Low-Rank Adaptation** fine-tunes without retraining the base model. Small low-rank matrices are trained beside the attention weights (the layer that relates tokens to each other). At inference those matrices are added to the frozen base weights. Storage, training, and inference stay small because the base model is unchanged.

An **adapter layer** puts the new information in a layer on top of the model instead. It works. LoRA usually works better.

## Knowledge bases

A **knowledge base** is Bedrock's RAG. Ingest from S3, a web crawler, SharePoint, Salesforce, Confluence, or a custom source. Structured or unstructured.

1. Parse. Default parser for plain text. **Bedrock Data Automation** when the source is a PDF, form, image, audio, or video and you need structured fields out of it. A foundation model as parser does the same kind of extraction and costs more.
2. Chunk, then embed with a model that supports embeddings (Titan or Cohere). You choose the vector dimension.
3. Store the chunk, its vector, and optional metadata.
4. Sync the data source. Creating the knowledge base does not index the files until you sync.

Vector store choices: **OpenSearch Serverless** is the exam default. Aurora PostgreSQL (pgvector) when the set is mid-size and you want SQL. Neptune Analytics for a graph. Also MemoryDB, MongoDB Atlas, Pinecone, and Redis Enterprise Cloud. S3 Vectors is the cheaper newer option; it was preview and out of exam scope at recording.

Use it from "chat with your document," from `Retrieve` / `RetrieveAndGenerate`, or as a tool on an agent (agentic RAG).

**OpenSearch Serverless does not scale to zero.** Deleting the knowledge base deletes the vectors, not the collection. An idle collection is on the order of $200 a month. Delete the collection in the OpenSearch Serverless dashboard when you are done. A knowledge base you will reuse for the agent lectures can stay up; anything else should come down. See [[1. Introduction]].

To build one: knowledge base with a vector store, IAM role (the console can create it), S3 data source, parser, chunking, embedding model, quick-create OpenSearch Serverless, then sync, then test with a generation model. The test view shows the retrieved chunks and citation metadata. Refresh the console if a new bucket does not appear.

## Chunking

**Chunking** is how a corpus is split before it is embedded. Too small and the hit has no thought in it. Too large and the hit is less relevant, and a small context window will drop or ignore it. Modern models take a large window; extra context can still throw the answer off.

| Strategy | What it does |
|---|---|
| Fixed size | N tokens per chunk plus an overlap so the edges of the previous chunk survive. Default is 300 tokens and it will not split a sentence. Overlap of 20% on a size of 5 is 1 token repeated on each side |
| No chunking | One chunk per file. You already split the corpus |
| Hierarchical | Search small child chunks for precision, then return the parent for the surrounding context. Child size, parent size, and overlap are separate |
| Semantic | A foundation model splits on topic, still honoring a max token size and sentence boundaries. You pay that model's tokens |

Semantic chunking also has a **buffer size** (how many neighboring sentences are considered; too big adds noise, too small drops context) and a **breakpoint percentile** (higher means fewer, larger, more distinct chunks).

A Lambda transformation function can sit in the ingest path and chunk or reshape records before they hit the vector store. You can also bring your own KMS key. The data-deletion policy defaults to deleting vectors when the data source is deleted, which still leaves the OpenSearch collection.

## Embeddings and search

An **embedding** is a high-dimensional vector whose position encodes meaning. Similar texts land near each other. Titan's default is 1024 or 1536 dimensions, often larger than the chunk it represents. Shrink the dimension to cut storage and transfer, then recheck retrieval on your own data. Complex domains need more dimensions.

**Dense** embeddings (the usual GenAI case) pack meaning into floating-point dimensions. **Sparse** vectors, such as one-hot, waste space; they give cleaner similarity scores in recommenders and are awkward to compress on a GPU. They are not the cost lever for a Bedrock knowledge base.

Lookup: embed the query, then take the $k$ nearest stored vectors. That is vector search. Indexes avoid a full scan. Closeness is usually **cosine similarity**: 1 when the vectors match, 0 when they are orthogonal.

**Metadata** rides along in a `metadata.json` and is not itself chunked. Typical fields: section, keywords, source document id, category, access control, lineage for citations. Retrieval can start with vector distance and then **rerank** with that metadata (hybrid search). Reranking is covered again later.

Keeping the index current: an S3 change can signal a Lambda that starts an ingestion job. Do not call `StartIngestionJob` on every PUT. Batch the updates on a schedule with EventBridge (and Batch if the volume is high) so you are not embedding one object at a time.

## Evaluating RAG

Three edges, three questions:

- Retrieved context vs the query: is the context relevant?
- Response vs that context: is the answer grounded (faithful)?
- Response vs the query: is the answer relevant, complete, correct?

Bedrock scores these with a second model as judge (**LLM-as-a-judge**). You supply a JSON dataset of prompts and reference answers. Reference contexts are optional and are required if you want a grounding score. Metrics include correctness, completeness, helpfulness, coherence, faithfulness, citation precision and coverage, harmfulness, stereotyping, and refusal. Different judge models (Nova, Llama, Mistral) score differently; more than one judge is how you check they agree. The judge prompt for a metric is itself a prompt, often a no / maybe / yes.

That job is offline. It does not block a live answer. Live blocking is a guardrail contextual grounding check. High vector similarity does not mean the answer is faithful.

## Multimodal models

A **multimodal** model encodes text, images, audio, video, or documents into one embedding space, so a photo of a shoe can retrieve catalog text and the reverse. Claude and Nova accept mixed input. Titan Multimodal Embeddings G1 is the embedding case: `inputText`, `inputImage`, or both. The image is base64 in the JSON, not a URL. Something in the pipeline (Glue, SageMaker, or Bedrock) has to do that encoding before the call.

## Guardrails

A **guardrail** filters prompts and responses for a knowledge base, an agent, or a single `Converse` call. Configure the message the user sees when something is blocked. You can use one message or a different one per filter. Optional: your own KMS key, and cross-region inference for throughput and for the newer filter tier.

What you can turn on:

- **Harmful categories** (hate, insults, and the rest), each with a threshold, on text and on images
- **Prompt attacks** ("ignore previous instructions"), block or detect. Off by default because of false positives. Set the strength (the demo uses medium)
- **Denied topics**, with a definition and sample phrases. Block or detect, separately for input and output
- **Word filters**: the built-in profanity list plus your own words, on input, output, or both
- **Sensitive information**: pick PII types and mask them or block. A custom regex is available for patterns the list misses
- **Contextual grounding**: a grounding threshold (response vs retrieved context) and a relevance threshold (response vs the question). Block or detect. Only as good as the chunks you retrieved. Off by default; it false-positives until you tune it

Content-filter tier **classic** covers English, French, and Spanish and stays in-region. **Standard** covers more languages and requires cross-region inference. A lot of newer Bedrock features require cross-region inference.

Attach the guardrail to the agent or knowledge base so it applies to every prompt and response. Test from the console and read the trace to see which filter fired. Guardrails are cheap to leave up; delete them if you will be away for a while.

### Automated reasoning checks

For a policy that is too branched for a topic filter (parental leave, a mortgage rule), Bedrock turns a clear, structured PDF into variables and logical rules and enforces them at the guardrail. API: `CreateAutomatedReasoningPolicy` with a name and the PDF. Start with a short policy and add rules once the extracted logic matches what you meant. At recording time this check was detect-only, a second look at the model's reasoning rather than a block.

## Token-level redaction

Guardrails are not the whole filter. A simpler layer can drop or mask text before it reaches the model and again before it reaches the user, including PII that arrived inside retrieved context.

Put a Lambda pre-handler and post-handler on the inference endpoint (Bedrock or SageMaker). The handler can be a word list or regex, or Amazon Comprehend named-entity recognition. The same filter belongs on the ingest path so the vector store never receives the sensitive tokens.

## Prompts

### Anatomy

Amazon's four parts:

1. **Instructions**: the task
2. **Context**: situation, or text you retrieved
3. **Input data**: the case to answer, including few-shot examples of the style you want
4. **Output indicator**: length, format, constraints. Put this at the end of the prompt

### Practices and types

Be specific. "Write something about books" is too open. Name the artifact ("a movie-script dialogue") and the shape ("each line at most two sentences"). Phrase the request as a question when you can. Give an example of the output so the model copies the format, not only the idea. Split a hard task into subtasks yourself; these models are weak at doing that unasked. If you are unsure it understood, ask.

**Chain-of-thought**: say "think step by step," and name the steps when you know them. You get a better answer and a trace of how it got there.

| Type | What you provide |
|---|---|
| Zero-shot | The task only. Works when the base model already knows the job |
| Few-shot | Example inputs and the exact outputs you want |
| Chain-of-thought | An instruction to decompose the problem, plus the steps if you have them |

Models are non-deterministic and they change. Keep trying prompts.

**Prompt engineering** in the AWS material also covers stuffing retrieved context into the prompt (RAG) and telling the model about tools it may call. Those are built as knowledge bases and agents later; the idea is the same.

### Misuse and bias

**Prompt injection** appends instructions that override the application's prompt ("ignore the above"). A fictional framing ("how would a character build this") is the same attack aimed at safety training. A system prompt that refuses those words helps and is still bypassable, because the user text can tell the model to ignore the system prompt. A guardrail on the output is the stronger layer. Use both.

**Prompt leaking**: "tell me your initial instructions" can dump the system prompt. Do not put secrets or internal codenames there. For PII, prefer not storing it. A guardrail that masks addresses, phone numbers, and IDs is the last filter.

Bias in the training data comes out in the output (the demo: "ten software engineers" rendered as the same young man, and the count was wrong). Say the diversity you want in the prompt, or show it with few-shot examples. A system prompt can demand it and can be leaked. The durable fix is the training set. You can also score generated images with a recognizer, or repair them after the fact with **counterfactual data augmentation** (segment the biased region and replace it). Two names, not the algorithms: **TIED** (text-to-image disambiguation) and **TAB** (text-to-image ambiguity benchmark).

### Prompt Management and Flows

**Prompt Management** stores a prompt so many apps share it. Versions support rollback. Variants exist per model or inference config. `{{genre}}` and `{{number}}` are variables filled at call time. You can attach tools and a caching strategy, a system prompt, and a KMS key. Names are letters, hyphens, and underscores. Test with sample variable values, save a draft, create a version, then use that version in a flow.

**Flows** (formerly prompt flows) chain nodes with connections, including conditions, in the console or as JSON. A node can be user input, a saved prompt, a knowledge-base retrieval, or the flow output. A small pattern: raw text in, a prompt that categorizes it, a condition, then either a knowledge base or a general prompt. Inputs can be structured fields, and you can put pre- and post-processing on them. This is the start of an agent built without application code.

### Structured output

Ask for JSON in the prompt: numbered instructions, the schema, an example of a valid object, nulls for missing fields, and an error shape when it fails. That schema is a **response format template**.

The other mechanism is tool use. `toolConfig` on Converse declares a tool whose arguments are the schema you want; the "tool" can simply be "emit this object." On current models the two methods score about the same. On older, smaller models, tool use was the reliable one. The exam point is that you can require structured JSON either way.

## Enterprise integration

Knowledge bases are the connector for enterprise content: S3 plus SharePoint, Confluence, Salesforce, and the other built-in sources, indexed into the vector store.

Cross-account semantic search, when the model and OpenSearch are in different accounts: an OpenSearch **remote inference connector** in the OpenSearch account calls Bedrock in the other account. The Bedrock account has a role that allows `bedrock:InvokeModel` from the OpenSearch account. Copying the index across, or refusing cross-account, is the wrong shape.

Between Bedrock and a system you do not control (warehouse, tickets, CRM), put a queue. A typical path is document upload → EventBridge → Lambda → Bedrock, then SQS or Kafka before the external system, so a downstream outage does not drop the event.

## Generative AI lens

The **AWS Well-Architected Generative AI Lens** is a set of best practices, not a service. It maps generative AI onto the six pillars: operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability. The exam can name it, and it can ask you to order the lifecycle:

1. Scope what the application is for
2. Select a model
3. Customize it (fine-tune or augment)
4. Develop and integrate
5. Deploy
6. Measure and improve, then scope the next pass

The course covers the practices. Read the lens once before the exam so the wording is familiar.
