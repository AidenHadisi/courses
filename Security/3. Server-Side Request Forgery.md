# Server-Side Request Forgery (SSRF)

Server-side request forgery occurs when an attacker induces a server-side application to make HTTP requests to an arbitrary, unintended destination. This exploits trust relationships where requests originating from the server bypass network perimeters, IP whitelists, or front-end authentication checks.

## Attack Targets

- **Localhost / loopback (`127.0.0.1`, `localhost`)**:
  - Edge reverse proxies and access control layers often enforce auth at the boundary, leaving internal application ports unauthenticated.
  - Applications may trust local connections for administrative tasks or disaster recovery without requiring credentials.
- **Internal backend infrastructure**:
  - Targets non-routable private IP addresses (e.g., `10.x.x.x`, `172.16.x.x`, `192.168.x.x`).
  - Backend services often have weaker security posture, assuming the surrounding network topology provides sufficient protection.
- **External systems**:
  - Forces the server to interact with third-party systems, potentially leaking credentials or routing attacks through the server's IP.

## Bypassing SSRF Defenses

Applications often attempt to sanitize or validate target URLs using blacklists or whitelists, which can be circumvented via parsing discrepancies or protocol behaviors.

### Blacklist Bypasses
- **Alternative IP representations**:
  - Decimal: `2130706433` (evaluates to `127.0.0.1`)
  - Octal: `017700000001`
  - Compact IP: `127.1`
- **DNS resolution**: Register a domain (or use services like `spoofed.burpcollaborator.net`) that points to `127.0.0.1`.
- **Obfuscation**: URL encoding (`%61dmin`), double encoding, or case variation.

### Whitelist Bypasses via URL Parsing
Ad-hoc regex and URL parsers often misidentify the destination host:

| Technique | Example | Mechanism |
|---|---|---|
| Userinfo credentials (`@`) | `https://expected-host@evil-host` | Parser treats text before `@` as host; client routes to `evil-host` |
| URL fragment (`#`) | `https://evil-host#expected-host` | Parser checks substring match; client ignores fragment in routing |
| DNS subdomains | `https://expected-host.evil-host` | Host matches prefix match check, but resolves to attacker-controlled domain |
| Encoding discrepancies | `https://expected-host%23@evil-host` | Server-side parser and HTTP request client decode at different stages |

### Bypasses via Open Redirection
If an application validates input against an allowlist, but the allowed domain contains an **open redirection** vulnerability:
1. Supply a whitelisted URL containing a redirect parameter:
   ```http
   POST /product/stock HTTP/1.0
   Content-Type: application/x-www-form-urlencoded

   stockApi=http://allowed-domain.com/redirect?url=http://192.168.0.68/admin
   ```
2. The initial URL passes the domain whitelist check.
3. The server's HTTP client follows the HTTP redirect (`302`) directly to the protected internal resource.

## Blind SSRF

**Blind SSRF** occurs when the server issues a backend HTTP request to the supplied URL, but the response is not returned in the front-end application interface.

### Detection via OAST
- Use Out-of-Band Application Security Testing (OAST) tools (e.g., Burp Collaborator) to supply unique listener hostnames and monitor for inbound requests.
- **DNS lookup without HTTP request**: Often indicates the outbound HTTP connection was blocked by firewall rules while outbound DNS resolution was permitted.

### Exploitation Strategies
- **Internal network scanning**: Blindly iterate through internal IP ranges and known endpoints with payloads designed to trigger out-of-band requests upon reaching unpatched internal services.
- **HTTP client exploits**: Coerce the backend into connecting to an attacker-controlled server that responds with payloads targeting parser vulnerabilities or memory corruption in the server's HTTP client library.

## Hidden Attack Surfaces

SSRF inputs are not always full URLs in visible request parameters:
- **Partial URL inputs**: Parameters accepting only a hostname, IP, or path segment appended server-side into a full request URL.
- **Embedded URLs in data formats**: Formats like XML parsed with external entity resolution enabled (SSRF via XXE).
- **HTTP Referer header**: Server-side analytics systems that crawl incoming `Referer` links to inspect anchor text or site contents.
