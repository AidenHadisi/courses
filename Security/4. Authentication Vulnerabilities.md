# Authentication Vulnerabilities

Authentication verifies the identity of a user, acting as the primary perimeter for application access. Vulnerabilities typically stem from inadequate brute-force defenses, predictable token generation, or flawed state verification logic across primary and supplementary account flows.

## Core Concepts

- **Authentication vs. Authorization**: Authentication verifies *who* a user is; authorization determines *what* permissions they have.
- **Authentication factors**:
  - **Knowledge**: Something you know (password, PIN, security answer).
  - **Possession**: Something you have (authenticator app, hardware key, SMS token).
  - **Inherence**: Something you are (biometrics, behavioral patterns).
- **True MFA**: Requires multiple distinct factor types. Re-verifying the same factor category (e.g., password + email verification code, both relying on knowledge) is dual-factor knowledge verification, not true MFA.

## Password Attacks and Enumeration

### Username Enumeration
Attackers analyze subtle behavioral differences to identify valid accounts before targeting passwords:
- **Error messages**: Asymmetric feedback (e.g., "Invalid username" vs. "Incorrect password", or missing punctuation in one variation).
- **HTTP status codes**: Returning `404` or `401` for unknown users versus `403` or `200` for existing users.
- **Timing discrepancies**: Valid usernames trigger additional operations (e.g., password hashing via bcrypt/argon2), resulting in measurable response delays. Delay can be amplified by supplying oversized password strings.

### Brute-Force Patterns
- **Password spraying**: Testing a small list of highly probable passwords against many candidate usernames to avoid account lockout thresholds.
- **Credential stuffing**: Replaying leaked username-password pairs across unrelated targets to exploit credential reuse across websites.
- **Human behavioral flaws**: Users satisfy complexity policies with predictable transforms (`Password1!`, incrementing numbers on forced rotations).

## Flawed Brute-Force Defenses

- **Account locking weaknesses**:
  - Does not prevent password spraying (each account receives only 1–2 attempts).
  - Vulnerable to Denial of Service (DoS) if an attacker intentionally locks out legitimate users.
  - Generates distinct "Account locked" messages that confirm valid usernames.
- **Rate limiting bypasses**:
  - **Counter resets**: Some systems reset failed attempt counters when the IP successfully logs in, allowing attackers to interleave their own valid credentials into brute-force dictionaries.
  - **IP spoofing**: Manipulating reverse-proxy headers (`X-Forwarded-For`, `X-Real-IP`, `Client-IP`).
  - **Batching**: Submitting multiple credential guesses within a single HTTP request (e.g., JSON payload arrays or GraphQL batching).

## HTTP Basic Authentication

The client transmits credentials encoded in Base64 on every request via the `Authorization` header:

```http
Authorization: Basic YWRtaW46cGFzc3dvcmQxMjM=
```

- **Vulnerabilities**:
  - Credentials remain static and are sent across every request; vulnerable to interception without strict HTTPS and HSTS.
  - Typically lacks integrated rate-limiting or lockout logic.
  - Inherent vulnerability to CSRF if used without separate anti-CSRF protections.

## Multi-Factor Authentication (MFA) Flaws

### Delivery Mechanisms
- **SMS / Email**: Insecure delivery channels. SMS is vulnerable to SIM swapping and SS7 interception; email collapses multiple steps into a single knowledge factor.
- **Dedicated TOTP / Hardware keys**: Authenticator apps (Google Authenticator) or FIDO2/WebAuthn hardware devices generate codes locally or use cryptographic challenges, eliminating transit interception.

### Implementation Bypasses
- **Direct navigation**: The application sets a full authentication session at step 1 (password entry) and only relies on client-side routing to prompt for step 2. Navigating directly to internal endpoints (e.g., `/dashboard`) bypasses 2FA.
- **Session/user decoupling**: Step 2 identifies the target user via a client-controlled parameter (e.g., `Cookie: account=victim` or hidden form input). An attacker logs into their own account, changes the cookie to the victim's identifier, and brute-forces the 2FA code.
- **2FA code brute-forcing**: 4- to 6-digit PINs have small keyspaces ($10^4$ to $10^6$ combinations). Without strict attempt limits, automated tools (Turbo Intruder) can crack codes within validity windows.

## Supplementary Authentication Flows

Supplementary account management functions often receive less security scrutiny than login endpoints:

### Persistent Sessions ("Remember Me")
- Insecure implementations store predictable concatenated strings (e.g., `base64(username + ":" + timestamp)` or unsalted hashes of passwords).
- If an attacker decodes the token construction schema, tokens for arbitrary users can be forged.
- Unsalted password hashes in cookies can be reversed via precomputed rainbow tables.

### Password Reset Workflows
- **User-controlled identifier**: Password reset links that specify targets by parameter rather than a cryptographically random token:
  ```http
  GET /reset-password?user=victim HTTP/1.1
  ```
- **Unvalidated tokens on submission**: The application validates a reset token when rendering the GET form, but fails to check token validity or ownership when processing the final POST submission.
- **Password reset poisoning**: Dynamic reset URL generation that incorporates unvalidated `Host` or `X-Forwarded-Host` headers, sending reset tokens to an attacker-controlled server.

### Password Change Endpoints
- Endpoints that accept user identifiers in parameters or body fields instead of resolving user context strictly from the server-side session.

## Defenses

| Mechanism | Vulnerability Addressed | Implementation Requirement |
|---|---|---|
| Generic error responses | Username enumeration | Return identical status codes, messages, and execution timing for all login outcomes |
| Dynamic rate limiting | Brute-force & spraying | Enforce IP- and account-level rate limits paired with CAPTCHAs upon threshold breach |
| Password strength meters | Predictable password creation | Use algorithmic complexity analyzers (e.g., `zxcvbn`) rather than rigid character rules |
| Cryptographic reset tokens | Reset hijacking | Generate high-entropy, single-use, time-bound tokens verified on both form GET and POST |
| Strict MFA session gating | 2FA bypass | Hold sessions in an unprivileged, non-authenticated state until all factors validate |
